# Технічне завдання
## Тестовий пет-проект №7: Distributed Order Matching Exchange
### (order book, розподілена координація, exactly-once розрахунки, chaos-тест)

---

## 1. Мета

Завдання перевіряє здатність працювати з системою, де правильність залежить не
лише від бізнес-логіки, а й від точного порядку подій під високим конкурентним
навантаженням: біржовий "рушій зіставлення заявок" (matching engine), де
мілісекунди й порядок обробки визначають, хто з клієнтів отримав кращу ціну.

Як і в попередньому завданні, кандидат стартує з частково готового
репозиторію (розділ 3) — потрібно розібратись у наявному коді, знайти
навмисно закладені проблеми і розвинути систему далі.

**Що перевіряємо додатково до попередніх завдань серії:**
- Коректність алгоритму зіставлення заявок (price-time priority) під
  конкурентним навантаженням — без псевдо-блокувань, які просто "здебільшого
  працюють"
- Розподілену координацію: лише один інстанс сервіса може бути "власником"
  конкретного інструмента (order book) у певний момент — і що відбувається,
  коли цей інстанс падає
- Побудову real-time потоку (order book depth) з коректним відновленням
  стану клієнта після розриву з'єднання (без "тихих" пропусків подій)
- Exactly-once розрахунки: угода (trade) повинна призвести до руху коштів
  рівно один раз, навіть якщо крок розрахунку виконується повторно після збою
- Обґрунтоване тестування стійкості до відмов (chaos-сценарій): що станеться
  із системою, якщо процес, що тримає розподілене блокування, впаде
  посередині операції
- Здатність читати систему, що вже частково працює під навантаженням, і не
  зламати наявну поведінку, вносячи виправлення

## 2. Стек технологій

| Шар | Технологія |
|---|---|
| Matching engine | NestJS (TypeScript), стан order book — in-memory на інстанс, з періодичною персистенцією |
| Settlement / Ledger | NestJS — окремий сервіс, що перетворює угоди (trades) на рух коштів (можна повторно використати ідеї з попереднього завдання: event sourcing, double-entry) |
| Frontend | Next.js (App Router, TypeScript) |
| База даних | PostgreSQL |
| Розподілена координація | Redis (розподілені блокування / лідер на інструмент) — з коректним TTL і renewal, або альтернатива на вибір (etcd, ZooKeeper) з обґрунтуванням |
| Черга подій | Kafka, Redis Streams або RabbitMQ — на вибір, з обґрунтуванням; критично — партиціонування за інструментом, щоб зберегти порядок подій в межах одного order book |
| Real-time | WebSocket з номерами послідовності (sequence numbers) для кожного оновлення order book |
| Автентифікація | JWT (access + refresh) |
| Спостережуваність | Структуроване логування з trace ID, `/metrics`, панель для перегляду стану order book і черги розрахунків |
| Контейнеризація | Docker + docker-compose (обов'язково) |

### 3.2 Що потрібно знайти й виправити самостійно

У наданому коді закладено кілька проблем із різних категорій. Точні локації
не розкриваються — це частина завдання. Орієнтовні категорії:

- Проблема конкурентного доступу до order book одного інструмента: два
  запити, що надходять практично одночасно, можуть бути оброблені в
  неправильному порядку відносно того, як вони фактично надійшли, або одна з
  заявок може "загубитися"/задвоїтися при зіставленні
- Розподілене блокування, яке за певних умов (аварійне завершення процесу,
  що тримає лок) може призвести до того, що інструмент "зависає" й ніхто не
  може його обробляти, або, навпаки, до того, що два інстанси одночасно
  вважають себе власником одного order book
- Місце, де користувач може вплинути на чужу заявку (скасувати чи змінити
  заявку, що йому не належить) через прямий виклик API
- Момент, де клієнт на фронтенді може "тихо" відстати від реального стану
  order book після розриву й перепідключення WebSocket, і не помітити цього
- Як мінімум один тест, що проходить незалежно від того, чи дійсно
  виконується заявлена в його назві поведінка

Кандидат має самостійно виявити ці місця, задокументувати кожну знахідку в
README (в чому проблема, як відтворити — бажано тестом чи сценарієм, як
виправлено) і виправити, не ламаючи іншу наявну функціональність без
пояснення.

### 3.3 Основне завдання поверх стартового коду

1. Усунути знайдені проблеми конкурентності й безпеки в matching engine
2. Реалізувати коректну розподілену координацію "один активний власник
   order book на інструмент" з graceful failover — якщо інстанс, що володіє
   інструментом, падає, інший інстанс має підхопити роботу без втрати чи
   задвоєння вже прийнятих заявок
3. Реалізувати exactly-once розрахунок угод у `settlement-service`: подія
   про угоду, доставлена (і оброблена) повторно, не повинна призвести до
   повторного руху коштів
4. Реалізувати коректне відновлення стану клієнта на фронтенді після
   розриву WebSocket-з'єднання (через sequence number: якщо клієнт бачить
   розрив послідовності — запитує повний знімок стану, а не продовжує
   мовчки з застарілими даними)
5. Провести й задокументувати chaos-тест: примусово "вбити" інстанс
   matching engine, що тримає блокування на інструмент, під час обробки
   заявок, і показати (тестом, логами чи скриптом відтворення), що система
   відновлюється коректно — без втрачених чи задвоєних заявок/угод

## 4. Суть проєкту: "Mini Exchange" — подача заявок, зіставлення, розрахунок

Спрощена біржа: користувачі подають лімітні заявки на купівлю/продаж по
кількох інструментах (наприклад, кілька умовних "тікерів"), система зіставляє
зустрічні заявки за принципом price-time priority, а результат (угоди)
проходить через окремий процес розрахунку, що змінює баланси гаманців
користувачів.

### 4.1 Функціональні вимоги

**Заявки (Orders)**
- Подача лімітної заявки: інструмент, напрям (buy/sell), ціна, кількість
- Скасування власної заявки (частково виконана заявка скасовується в
  залишку)
- Перегляд власних активних і виконаних заявок
- Захист від self-trade: заявки одного й того самого користувача не повинні
  зіставлятись одна з одною

**Order Book**
- Зіставлення нової заявки з наявними протилежними заявками за
  price-time priority: краща ціна першою, за рівної ціни — раніше подана
  заявка першою
- Часткове виконання заявки (одна заявка може закрити кілька зустрічних
  часткових обсягів або бути закритою кількома контрагентами)
- Публічний перегляд глибини order book (агреговані обсяги по рівнях ціни)
  в реальному часі через WebSocket
- Клієнт, що перепідключився після розриву, повинен отримати коректний
  поточний стан order book, а не продовжувати з можливо застарілими даними

**Розрахунок угод (Settlement)**
- Кожна угода (matched trade) публікується як подія й асинхронно
  обробляється `settlement-service`, який змінює баланси гаманців
  покупця і продавця
- Обробка події угоди — ідемпотентна: повторна доставка того самого trade ID
  не повинна подвоїти рух коштів
- Реконсиляція: сума угод за період, помножена на ціни, має узгоджуватись із
  сумарним рухом коштів на гаманцях — потрібен ендпоінт/скрипт звірки

**Розподілена координація**
- У будь-який момент часу лише один інстанс `matching-engine-service`
  обробляє заявки для конкретного інструмента (запобігання одночасній
  обробці одного order book двома інстансами)
- При падінні інстанса, що володіє інструментом, інший інстанс має
  перебрати обробку протягом обмеженого часу (позначте очікуваний
  максимальний час простою інструмента в README)

**Frontend (Next.js)**
- Форма подачі заявки (інструмент, напрям, ціна, кількість), список власних
  активних заявок зі скасуванням
- Сторінка order book з живим оновленням глибини ринку (Client Component,
  WebSocket) і коректним resync після розриву з'єднання
- Стрічка останніх угод по інструменту
- Стани loading/empty/error, індикатор стану з'єднання (live/reconnecting/
  stale — коли клієнт виявив розрив послідовності й запитує повний знімок)

### 4.2 Нефункціональні вимоги

- Порядок обробки заявок по одному інструменту має відповідати порядку їх
  фактичного надходження (в межах гарантій обраної черги/координації) —
  опишіть явно, які гарантії порядку забезпечує обраний брокер і як це
  узгоджується з вимогою до order book
- Ідемпотентність обробки подій угод у `settlement-service`
- Явна стратегія graceful failover для розподіленого власника інструмента
  (TTL блокування, механізм renewal, поведінка при "split-brain" ризику)
- Валідація вхідних даних на всіх шарах, захист від основних вразливостей,
  включно з IDOR на заявках і гаманцях
- Rate limiting на подачу заявок (запобігання спаму/флуду одним клієнтом)
- Структуроване логування з trace/correlation ID через увесь шлях: заявка →
  зіставлення → угода → розрахунок
- Конфігурація через `.env`, `.env.example`
- CI pipeline (лінт, типчек, тести) на push/PR; наявний CI не повинен
  зламатись без задокументованої причини

## 5. Архітектурні вимоги

- Явний опис моделі узгодженості order book: чому обраний підхід
  (наприклад, single-writer per instrument через розподілене блокування,
  або партиціонування черги за інструментом) гарантує правильний порядок
  зіставлення
- Явний опис стратегії failover: хто і як виявляє, що власник інструмента
  недоступний, скільки часу займає перехоплення, чи можлива втрата чи
  задвоєння заявок у цьому вікні і як це мінімізовано
- Явна діаграма шляху даних: заявка → matching engine → подія угоди →
  чергу → settlement-service → зміна балансу → WebSocket-сповіщення клієнту
- Опис ідемпотентної обробки на межі `settlement-service`
- Індекси в БД для полів, що використовуються в реконсиляції й перевірках
  прав доступу до заявок/гаманців

## 6. Тестування

- Unit-тести для ключової бізнес-логіки: алгоритм зіставлення заявок
  (price-time priority, часткове виконання, self-trade prevention),
  ідемпотентна обробка події угоди в settlement-service
- Тест на конкурентність: паралельна подача кількох заявок до одного
  інструмента — перевірка, що фінальний стан order book і список угод
  коректні й детерміновані щодо порядку надходження
- Chaos-тест (чи скрипт відтворення з описом результату в README):
  примусове завершення інстанса, що володіє інструментом, у процесі обробки
  заявок — перевірка, що інший інстанс перебирає роботу і жодна заявка не
  губиться й не обробляється двічі
- Тест на ідемпотентність розрахунку: повторна доставка тієї самої події
  угоди — баланс змінюється рівно один раз
- Тест(и), що відтворюють знайдені в стартовому коді проблеми (розділ 3.2)
- Наявні в стартовому репозиторії тести мають лишитись зеленими (або зміна
  явно обґрунтована в README)
- Опційно: тест reconnect/resync-логіки WebSocket на фронтенді

## 9. Що НЕ є метою

- Реальна фінансова біржа з реальними активами чи інтеграцією з ринками —
  усе в межах симуляції
- Мікросекундна латентність чи оптимізація продуктивності на рівні
  промислових HFT-систем — важлива коректність, а не швидкість у наносекундах
- Підтримка складних типів заявок (stop-loss, iceberg, OCO тощо) — досить
  простих лімітних заявок
- Повноцінна система управління ризиками чи маржинальна торгівля
- Ідеальний дизайн UI
- 100% покриття тестами
- Переписування наданого стартового коду "з нуля" там, де це не продиктовано
  явною потребою
